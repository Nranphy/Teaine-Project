# Teaine Grail 架构设计文档

## 1. 项目目标

Teaine Grail 是 Project Teaine 中负责 Agent 互动编排的本地运行服务。系统接收来自外界的事件与日志，构造上下文，驱动 Agent 进行推理与工具调用，并将结果投递到演出输出链路，最终形成文本、TTS、Live2D 动作等多模态反馈。

本项目的核心目标如下：

- 在本地稳定运行 Agent 互动流程。
- 以异步方式处理事件、推理、工具调用与输出编排。
- 支持短期记忆与长期记忆，并提供统一的检索与写入策略。
- 将 Agent 能力与 Tool 实现解耦，便于扩展和替换。
- 为后续管理接口、观测能力和多 Agent 扩展预留清晰边界。

## 2. 设计原则

- 事件驱动：系统围绕事件与日志触发运行，而不是围绕单次请求同步执行。
- 编排与执行分离：Agent 决定“做什么”，运行时系统决定“如何可靠执行”。
- Prompt 组件化：基础设定、时间信息、历史上下文、记忆召回、工具说明分别构造，再统一组装。
- Tool 解耦：Tool 通过统一接口注册与调用，不与具体模型实现直接耦合。
- 可恢复与可观测：每次运行都应具备唯一标识、状态流转、日志记录与失败恢复能力。

## 3. 系统边界

Teaine Grail 负责以下职责：

- 接收外部事件和日志输入。
- 构建 Agent 运行上下文。
- 调用大模型完成推理与工具决策。
- 调度 Tool 执行并管理回合。
- 将最终结果写入输出链路。
- 管理短期记忆与长期记忆的读写流程。

Teaine Grail 不直接负责以下职责：

- 具体的语音合成实现。
- 具体的 Live2D 渲染与播控实现。
- 图片识别模型的底层推理实现。
- 长期记忆向量库的底层存储细节。

这些能力应通过外部服务或可替换的基础设施模块接入。

## 4. 核心运行流程

系统主流程如下：

`事件/日志输入 -> 触发器判定 -> 创建运行实例 -> Prompt 构造 -> Agent Loop -> Tool 执行 -> 输出编排 -> 结果落库`

详细说明如下：

1. 外界事件进入日志表或事件流。
2. 触发器根据规则判断是否应启动一次 Agent 运行。
3. 系统创建一个新的 `run`，并绑定对应会话上下文。
4. Prompt Builder 收集人设、当前时间、历史日志、记忆召回结果、工具说明等内容，构造基础上下文。
5. Agent 进入推理循环，决定直接回复或调用一个或多个 Tool。
6. Runtime 执行 Tool，并将执行结果回填到后续上下文中。
7. 当满足结束条件时，生成最终输出并提交到演出队列。
8. 运行结果、记忆写入结果、输出结果和异常信息统一记录。

## 5. 运行时对象模型

为避免日志、会话、执行实例之间混淆，系统定义以下运行时对象：

### 5.1 Event

`Event` 表示一次来自外部世界的原始输入，例如：

- 弹幕消息
- 用户文本输入
- 操作指令
- 定时触发事件
- 外部订阅事件

`Event` 是不可变输入，只负责描述发生了什么。

### 5.2 Session

`Session` 表示一段连续互动上下文，用于归档同一来源、同一角色或同一房间的连续对话状态。Session 负责承载：

- 最近日志窗口
- 短期记忆引用
- 当前角色状态
- 节流与并发控制信息

### 5.3 Run

`Run` 表示一次由触发器创建的 Agent 执行实例。每个 Run 应具备唯一 `run_id`，并记录：

- 触发来源
- 输入事件范围
- 绑定的 session
- Prompt 构造结果
- Tool 调用记录
- 最终输出
- 状态流转
- 错误信息

`Run` 的状态建议至少包括：

- `pending`
- `running`
- `waiting_tool`
- `completed`
- `failed`
- `cancelled`

## 6. 触发与调度模型

系统支持以下几类触发方式：

- 定时任务触发
- 关键事件订阅触发
- 管理接口主动触发

触发器不直接执行 Agent，而是负责创建 Run 请求并交给调度层。调度层应负责：

- 决定是否与已有运行合并
- 控制同一 Session 是否允许并发运行
- 为 Run 分配执行资源
- 处理超时、取消、重试等生命周期行为

建议默认策略如下：

- 同一 Session 在同一时刻只允许一个活跃 Run。
- 新事件到达时，如果已有 Run 正在执行，则进入等待队列或合并窗口。
- 对高频输入使用时间窗口聚合，避免每条日志都单独触发模型调用。

## 7. Prompt 构造层

Prompt 不应直接由单个函数拼接，而应由独立的 Prompt Builder 完成。Builder 至少由以下部分组成：

- 角色设定
- 当前日期时间
- 当前触发原因
- 最近日志摘要或窗口
- 相关短期记忆
- 相关长期记忆
- Tool 说明
- 行为约束与安全约束

建议采用“组件生成后统一装配”的方式，避免后续难以维护。

Prompt Builder 的职责是：

- 控制上下文长度
- 控制不同信息块优先级
- 确保格式稳定
- 在缺失部分信息时进行合理降级

## 8. 记忆系统设计

系统中的记忆分为短期记忆与长期记忆。

### 8.1 短期记忆

短期记忆用于支撑当前 Session 内的连续互动，通常来自：

- 最近若干轮对话
- 最近重要事件摘要
- 当前运行过程中的中间结论

短期记忆应优先保证低延迟读取，可直接保存在本地数据库、缓存或会话状态中。

### 8.2 长期记忆

长期记忆用于保存对后续互动有持续价值的信息，例如：

- 用户偏好
- 长期设定
- 稳定背景知识
- 历史重要事件总结

长期记忆建议以“摘要后写入”的方式进入向量库，而不是将所有原始日志直接写入。

### 8.3 记忆读写策略

建议遵循以下流程：

1. 运行前先读取短期记忆。
2. 根据当前事件生成检索查询，从长期记忆中召回候选内容。
3. 对召回结果进行数量限制与相关性筛选。
4. 运行结束后，由专门策略判断是否写入新记忆。
5. 写入长期记忆前先进行归纳、去噪和去重。

需要特别考虑的问题包括：

- 错误记忆的修正机制
- 重复记忆的合并策略
- 不同类型记忆的 TTL 或失效规则

## 9. Agent Loop 设计

Agent Loop 是运行时的核心控制逻辑。一次 Run 中，Agent 可在多个回合内进行推理与工具调用。

每个回合只允许以下几类结果：

- 直接给出最终回复
- 发起一个或多个 Tool 调用
- 主动终止当前运行

Loop 的终止条件应至少包括：

- Agent 返回最终输出
- 达到最大回合数
- 总运行时间超过限制
- 工具调用连续失败达到阈值
- 被调度器或管理接口取消

建议在 Runtime 中而不是模型提示中强制这些限制，这样可以避免模型不遵守时影响系统稳定性。

## 10. Tool 架构

Tool 是 Agent 可调用的能力单元。Tool 应具备统一接口，并由 Tool Registry 管理注册、发现与调用。

建议 Tool 统一包含以下元信息：

- tool_name
- 输入参数定义
- 输出结果定义
- 是否有副作用
- 是否可重试
- 超时时间

按照职责，Tool 可分为两类：

- 只读 Tool：如记忆搜索、图片解释、状态查询
- 有副作用 Tool：如写入记忆、提交输出、写入外部状态

当前阶段建议至少定义以下 Tool：

- `search_memory(query) -> memory_list`
- `save_memory(type, content) -> result`
- `describe_image(path, instruction) -> text`
- `enqueue_output(text, emotion) -> result`

其中 `enqueue_output` 只负责向演出队列投递结构化内容，不负责直接执行 TTS 或 Live2D 播放。后续演出系统再异步消费该队列并完成具体输出。

## 11. 输出编排层

为了避免 Agent 与具体表现层耦合，输出流程建议拆为两层：

- Agent 输出层：只生成文本、情绪、动作意图、优先级等结构化结果
- 演出编排层：将结构化结果转换为文本输出、TTS 请求、Live2D 动作队列等

这样可以带来以下好处：

- 更换表现引擎时不影响 Agent 逻辑
- 同一条语义输出可映射到不同终端
- 失败重试时可以在输出层局部恢复

## 12. 失败处理与幂等

系统必须从一开始就考虑失败恢复与重复执行问题。

### 12.1 失败分类

- 模型调用失败
- Tool 执行失败
- 外部服务超时
- 输出链路失败
- 记忆写入失败

### 12.2 处理原则

- 只读 Tool 可优先重试。
- 有副作用 Tool 必须具备幂等键或重复提交保护。
- 输出投递必须避免重复播报。
- 长期记忆写入必须避免重复插入。
- 当部分步骤失败时，Run 应可记录为部分成功，而不是简单视为整体失败。

## 13. 可观测性

系统应为每次 Run 建立完整观测信息，至少包括：

- `run_id`
- `session_id`
- 触发来源
- 输入事件数量
- Prompt 大小
- 模型调用耗时
- Tool 调用明细
- 最终输出内容摘要
- 错误与异常堆栈

建议保留结构化日志，便于后续接入：

- 本地调试面板
- 管理接口查询
- 回放与问题定位工具

## 14. 模块划分建议

建议初期按如下模块组织：

- `ingress`
  负责接收事件、日志和外部触发。
- `scheduler`
  负责触发判定、Run 创建、队列与并发控制。
- `prompting`
  负责基础 Prompt、上下文装配和长度控制。
- `runtime`
  负责 Agent Loop、状态流转和 Tool 执行编排。
- `tools`
  负责 Tool 注册、定义与实现。
- `memory`
  负责短期记忆与长期记忆的读写。
- `output`
  负责输出事件入队和演出编排对接。
- `api`
  负责管理接口与状态查询接口。

## 15. 当前版本的实现优先级

建议按以下顺序推进实现：

1. 明确 `Event / Session / Run` 数据模型。
2. 建立基础 Prompt Builder。
3. 实现 Tool Registry 与统一 Tool 接口。
4. 打通单 Session 单 Run 的 Agent Loop。
5. 接入短期记忆与长期记忆检索。
6. 接入输出队列。
7. 补齐调度、重试、可观测与管理接口。

## 16. 后续扩展方向

本架构未来可继续支持以下扩展：

- 多 Agent 协作
- 多角色切换
- 更复杂的事件优先级调度
- 更细粒度的演出编排
- 多模态输入扩展
- 更完整的记忆治理机制

本文件的目标不是规定所有实现细节，而是先明确系统边界、运行时对象、主要责任划分与关键约束，确保后续实现始终围绕稳定、可扩展和可观测三个方向推进。
