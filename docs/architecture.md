# Project Teaine 架构设计

## 1. 目标

Project Teaine 是一个分布式、以本地优先为核心的虚拟 Agent 系统。项目被拆分为多个服务，使运行时编排、云端协调、平台接入和演出执行可以独立演进。

当前服务集合如下：

- `Ruler`：中心服务与共享控制面
- `Grail`：本地 Agent 运行时与编排引擎
- `Caster`：本地演出执行器，负责 Live2D、语音和文本输出
- `Archer`：平台入口采集器，负责弹幕和外部事件接入
- `Rider`：本地管理界面
- `Common`：公共模型、协议与工具

整个架构遵循以下原则：

- 本地优先，保证低延迟的 Agent 行为
- 明确区分控制面与执行面
- 以协议边界为核心，而不是以实现细节为核心
- 基础设施可替换
- 从一开始就考虑可观测性与故障恢复

## 2. 服务职责

### 2.1 Ruler

`Ruler` 是共享控制面。它负责面向云端的协调和共享数据，但不应该演变成 Agent 运行时本身。

主要职责：

- 托管管理接口和集成接口
- 接收来自 `Archer` 等远端采集器上传的事件
- 持久化共享元数据、配置和跨设备状态
- 管理账号、身份、权限和服务注册
- 向 `Rider` 和本地服务暴露查询与控制接口
- 记录运行元数据、索引、摘要和可观测性数据

非职责：

- 执行完整的 Agent Loop
- 直接驱动 Live2D 或 TTS 输出
- 承担平台适配采集逻辑

### 2.2 Grail

`Grail` 是本地 Agent 执行引擎，负责上下文构造、推理循环、工具调度和交互流程。

主要职责：

- 接收本地触发或同步触发
- 构造 Prompt 上下文
- 执行 Agent Loop
- 调用工具并管理中间状态
- 管理短期记忆和本地运行时状态
- 决定输出意图，并向 `Caster` 下发执行命令
- 在需要时把部分状态和结果回传给 `Ruler`

非职责：

- 持有共享云端身份和全局配置
- 直接接入所有外部平台

### 2.3 Caster

`Caster` 是本地表现层。它将结构化输出意图转换为实际的演出行为。

主要职责：

- 控制 Live2D 动作和表情播放
- 执行 TTS 请求和语音播放
- 渲染或转发文本输出
- 管理播放队列和本地设备状态
- 将执行结果和失败信息回报给 `Grail`

`Caster` 应保持为本地执行器，而不是承载云端业务规则。

### 2.4 Archer

`Archer` 是第三方平台的入口适配层。

主要职责：

- 连接平台侧事件源
- 将平台负载归一化为 Teaine 的事件协议
- 把标准化事件上传到 `Ruler`
- 处理重试、去重以及来源侧元数据

`Archer` 不应包含 Agent 逻辑，它只是采集器和适配器。

### 2.5 Rider

`Rider` 是用于管理本地服务和同步状态的界面程序。

主要职责：

- 展示本地服务健康状态和运行状态
- 管理本地配置和运行控制
- 查看 Session、Run、日志和待播放输出
- 在需要时通过 `Ruler` 管理云端同步配置

`Rider` 应尽量保持轻量，业务行为应位于服务层，而不是 UI 层。

### 2.6 Common

`Common` 存放跨服务稳定共享的定义。

建议内容：

- DTO 和协议模型
- 枚举和错误码
- 共享类型定义
- 不依赖具体服务运行时的纯工具函数

不建议放入 `Common` 的内容：

- 服务专属的数据库访问逻辑
- 隐式依赖运行时环境的单例
- 业务编排逻辑
- 强迫所有服务共享同一套基础设施栈的模块

## 3. 控制面与执行面

整个项目应被明确拆分成两层。

### 3.1 控制面

控制面以 `Ruler` 为中心。

它负责：

- 共享持久化
- 用户和服务身份
- 管理接口
- 跨设备配置
- 事件接入与索引
- 协调元数据

### 3.2 执行面

执行面是本地且对延迟敏感的。

它包括：

- `Grail`，负责 Agent 编排
- `Caster`，负责输出执行
- `Archer`，负责来源侧采集
- `Rider`，负责本地观测和运维

这种拆分可以在保持本地运行时自治的同时，让云端层保持可替换。

## 4. 推荐的数据归属

数据归属必须明确。共享数据归 `Ruler`，瞬时执行状态归本地服务。

### 4.1 适合放在 Ruler 的数据

- 用户账号和身份
- 服务注册信息和节点元数据
- 平台连接元数据
- 标准化外部事件记录
- Session 索引和可检索摘要
- 长生命周期配置
- 审计日志和操作历史
- 全局记忆索引或引用

### 4.2 适合由 Grail 本地保存的数据

- 活跃 Run 状态
- Prompt 组装中的中间结果
- 临时工具结果
- 本地短期记忆窗口
- 输出规划状态
- 进行中的调度状态

### 4.3 适合由 Caster 本地保存的数据

- 播放队列
- 设备能力状态
- 音频或素材的本地缓存
- 用于恢复的演出执行历史

## 5. 服务间通信规则

为了让系统可调试，通信路径应该尽量窄且有明确意图。

推荐通信路径：

- `Archer -> Ruler`
- `Rider -> Ruler`
- `Grail -> Ruler`
- `Grail -> Caster`
- `Rider -> Grail`
- `Rider -> Caster`

除非有充分理由，否则应避免以下路径：

- `Archer -> Grail` 的直接运行时注入
- `Archer -> Caster`
- `Ruler -> Caster` 的直接演出控制
- `Rider` 与内部业务逻辑的重耦合

核心规则是：

`Ruler` 作为共享协调中心，`Grail` 作为本地 Agent 行为编排中心。

## 6. 事件驱动模型

这个项目不是单纯的 CRUD 后端，而是事件驱动系统。因此，协议设计比 ORM 选型更重要。

核心运行时对象建议统一为：

- `Event`：不可变的外部或内部输入
- `Session`：一段连续交互上下文
- `Run`：一次 Agent 执行实例
- `Task`：Run 内部或相关联的可调度工作单元
- `OutputIntent`：`Grail` 生成的结构化输出意图
- `PerformanceJob`：发送给 `Caster` 的可执行指令

每个重要协议对象都应定义：

- 唯一标识
- 来源
- 时间戳
- 在需要时记录因果父级标识
- 状态
- 在可重放场景下的幂等键

## 7. 运行时生命周期

期望的主流程是：

`平台输入 -> Archer -> Ruler -> 触发/同步 -> Grail -> 工具循环 -> OutputIntent -> Caster -> 演出结果 -> 同步/记录`

详细过程如下：

1. `Archer` 接收到平台事件。
2. `Archer` 将事件标准化后上传到 `Ruler`。
3. `Ruler` 持久化事件，并更新相关 Session 或路由元数据。
4. `Grail` 从 `Ruler` 拉取或接收相关触发。
5. `Grail` 构建运行时上下文并启动一个 `Run`。
6. `Grail` 执行推理和工具调用。
7. `Grail` 产出一个 `OutputIntent`。
8. `Caster` 将输出执行为文本、语音和动作表现。
9. 结果、摘要和遥测信息写回本地存储，并在需要时同步到 `Ruler`。

## 8. Supabase 的定位建议

对于这个项目，`Supabase` 更适合作为 `Ruler` 的基础设施，而不是所有服务通用的运行时抽象。

推荐立场如下：

- 主要在 `Ruler` 中使用 `Supabase`
- 保持 `Grail` 的本地自治
- 不要让 `Supabase SDK` 渗透到所有服务中
- 保持共享协议独立于任何单一后端厂商

这样设计的原因是：

- `Ruler` 天然适合作为托管控制面
- `Supabase` 可以提供托管 Postgres、Auth、Storage 和 Realtime 能力
- `Rider` 后续也更容易利用同步和管理接口
- 本地运行时服务依然保持可测试和可迁移

这样可以在获得 `Supabase` 便利性的同时，避免整个系统被平台强耦合。

## 9. 持久化策略

持久化应分层设计。

### 9.1 共享持久化

`Ruler` 可以使用 `Supabase` 这类托管后端承载：

- 持久化关系数据
- 鉴权与访问控制
- 存储元数据
- Realtime 协调通道

### 9.2 本地持久化

`Grail` 和 `Caster` 应保留本地持久化能力，用于：

- 低延迟状态访问
- 离线运行
- 进程重启后的恢复
- 临时执行窗口保存

这意味着架构层面应默认支持一定程度的离线能力，即使 `Ruler` 不可用时也能局部工作。

## 10. Common 库约束

`Teaine-Common` 应首先被视为协议和共享类型包。

建议结构：

- `models/`
  存放共享协议模型和通用值对象
- `models/db/`
  只放数据库无关的稳定类型和枚举
- `utils/`
  未来需要时可放纯工具函数
- `docs/`
  存放这类跨项目文档

新增共享类型时，优先考虑：

- 请求和响应 DTO
- 事件模型
- 状态枚举
- 消息结构

除非多个服务真的依赖完全相同的契约，否则不要把服务私有的持久化 Schema 放进这里。

## 11. 可观测性

每个服务都应输出结构化日志和可识别的生命周期元数据。

建议跨服务统一字段至少包括：

- `service_name`
- `instance_id`
- `session_id`
- `run_id`
- `event_id`
- `task_id`
- `trace_id`
- `timestamp`
- `status`

重要观测指标包括：

- 接入延迟
- Run 执行时长
- 工具执行时长
- 输出队列等待时长
- 播放延迟
- 同步失败次数

## 12. 需要尽早控制的风险

架构上的主要风险不是技术新颖性，而是失控的耦合。

关键风险包括：

- `Ruler` 膨胀成万能中心服务
- `Common` 演变成大杂烩
- 服务之间直接发生业务级强耦合
- 控制状态和执行状态混杂
- 缺少幂等和重放规则
- `Event`、`Session`、`Run` 的状态模型过弱

这些问题应该在实现深入之前尽早控制。

## 13. 近期优先事项

推荐的推进顺序：

1. 在 `Common` 中定义共享协议对象
2. 明确各服务边界和归属
3. 统一运行时生命周期和状态枚举
4. 设计 `Ruler` 的共享状态和事件接入数据模型
5. 定义 `Grail <-> Caster` 的命令与结果协议
6. 定义 `Archer -> Ruler` 的上传契约
7. 优先把 `Rider` 做成观测和运维界面

## 14. 总结

Project Teaine 应被视为一个本地优先、带有托管控制面的分布式系统。

当前最稳的架构方向是：

- `Ruler` 作为共享控制面，并可由 `Supabase` 提供基础设施支持
- `Grail` 作为本地 Agent 编排核心
- `Caster` 作为本地演出执行器
- `Archer` 作为入口归一化与上传组件
- `Rider` 作为运维与管理界面
- `Common` 作为协议和共享模型包

这种设计能在保持模块边界清晰的同时，降低平台锁定风险，并让 `Supabase` 只在最适合的层面发挥作用。
